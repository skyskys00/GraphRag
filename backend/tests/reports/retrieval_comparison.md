> 测试集：`testset_cservice_35.json`（客服业务库，35 题） | 模式：retrieval | collection：`eval_cservice`

> **优化目标**：提升 `table_numeric`（表格数字题）类目的 Context Precision

## 版本演进

- **v5.6 基线**：表格内容为 HTML 格式；数字感知、表格双表示均未上线
- **v5.7 表格双表示**：表格 TextUnit：content 改 Markdown（embedding用）+ html 字段（预览用）；GT 修正
- **v5.8 切分调细+数字token**：TABLE_SPLIT_ROWS 5→3；数字型问题 token 追加 keyword 路（1x 权重）
- **v5.8.2 表格boost×1.2**：RRF 融合后表格 chunk ×1.2 权重 → **无效**（结果与 v5.8 完全一致）
- **v5.8.2b 表格boost×2.0**：RRF 融合后表格 chunk ×2.0 权重 → **无效**（top40 中 table 已够多，rerank 决定最终排名）
- **v5.9 特征融合**：rerank/sparse/rrf/numeric_match/numeric_density 五特征加权融合排序 → top8 总量与 v5.8.2b 持平，类目微调（fact_single -，proper_noun/summary +）
- **v5.9-top5**：RERANK_TOP 8→5，检索只返回 5 块（同融合权重）→ **CP 全类目上升，Recall 0.9202 无损**
- **v5.10 列名前缀**：表格块 content 前置「【表格：caption | 列：列名1|...】」，dense+sparse 同时受益 → 总体 CP 微降（-0.011），**table_numeric Recall 0.792→0.917（+0.125）**，CP 持平 0.40
- **v5.11 table_numeric_boost=2.0**：数字型问题中表格块 numeric_match ×2.0 增益 → **零效果**（与 v5.10 完全一致）
- **v5.12 numeric_match bug 修复 + 增益**：修复 1 位数字过滤 + 空格不匹配两个 bug，再叠加 table_numeric_boost → **仍零效果**（与 v5.10 完全一致）

## 结论与观察

1. **v5.6 → v5.7 最大跃升**：table_numeric precision 0.0625 → 0.2188（+250%），表格内容从 HTML 改 Markdown 对 embedding 质量提升显著。
2. **v5.7 → v5.8 持续改善**：table_numeric precision 0.2188 → 0.2812（+28%），切分调细 + 数字 token 追加有效。
3. **RRF 阶段 table boost 无效**：×1.2 和 ×2.0 结果完全相同 —— 因为 top40 候选里 table chunk 已足够多，最终排名由 rerank 决定。
4. **v5.9 特征融合在 top8 下总量持平**：类目上有小额替换（fact_single -0.025、proper_noun +0.021、summary +0.063），方向上对无表格语义类目更友好，但 top8 的 0-3 位噪音块未被解决。
5. **v5.9-top5 是迄今最大精度跃升**：CP 0.4250 → 0.5657（+0.141），加权 0.6817（+0.078），**全部类目 CP 上升、Recall 0.9202 无损**。原因是 rank6-8 恰好是噪音重灾区（35 题相关块 83% 落在 rank1-5），top5 直接砍掉噪音分母。
6. **top5 代价集中在一题**：CS-FC-001 的核心表格块在 rank7，被挤出后 CP 0.375→0.200；recall 不受影响（该事实在前 5 有其他段落兜住）。生成侧若依赖该块可能细节缺失，需 answer 模式验证。
7. **下一步方向**：①线上切 RERANK_TOP=5 后跑 answer 模式验证生成质量；②看情况对 top5 前 5 排序抖动更敏感，可评估在候选池内做跨文档保底（每文档至少保留 1 块，覆盖 CS-FC-001 场景）。
8. **v5.10 列名前缀 → 纯 Recall 收益，但来源需修正**：总体 Recall 0.9202 → 0.9323（+0.012）、CP 微降 0.5657 → 0.5543；table_numeric Recall 0.792 → 0.917（+0.125）是本轮真正拐点。**逐题核对后归因修正**：类目增益全部来自 **CS-TN-004（2/4→4/4）**，CS-TN-003 全版本恒 0.667（早期记录「0.333→0.667，提升集中在 CS-TN-003」有误）。列名前缀给表格块加自然语言列名框架，dense/sparse 召回与 judge 推导同时受益，但它对 CS-TN-003 的市场规模表无效（见 #9 探针）。
9. **v5.11/v5.12 numeric_match 增益 → 完全无效**：数值型问题中表格块 numeric_match ×2.0（v5.11）叠加 1 位数字/空格匹配修复（v5.12）后，检索结果与 v5.10 逐字节一致。根因：**四道 table_numeric 题中三题 Recall 已满（1.0），剩下一题差的是 rank6 之外的补充块，numeric_match 类的跨类特征只能调整已经在 top5 里的相关块之间的相对排序，无法把噪音块（CP 分母）替换掉** → CP 不动，Recall 不动。**探针实测（CS-TN-003，v5.10 索引）**：2023 年市场规模表块（chunk-3e7b9f…）graph/vector/kw 三路都召回、RRF 池第 7，但 bge-reranker 只给 0.1328，融合后落到**第 13 名**。到 rank5 的融合分差约 0.31，numeric_match 权重仅 0.15，boost 封顶也补不上——该类目缺口是 **reranker 对数字表语义失明**，既不是候选缺口（块在池内），也不是 top5/top8 窗口缺口（top8 同样丢）。
10. **CP=0.40 的本质**：table_numeric 题目本身相关块就少（答案高度集中在 1-2 个表格块），top5 中其余位是上下文块。CP 0.40 对应「每 5 块中约 2 块直接相关」，这是分母约束下的合理值。后续若要继续升 CP，需换特征思路（如列名匹配、非表格块减分），而不是增强数字匹配。
11. **v5.10 生成端实测（4 题 table_numeric）**：答案质量与 CP 数字脱钩——CS-TN-001/002/004 三题在 CP 只有 0.4~0.8 的情况下**答案完全正确**（数值全对、引用正确、无幻觉），CS-TN-003 部分正确（2026E=425 亿答对，但 2023 年市场规模表格块 chunk-003 未进 top5，如实说明「材料未提供」而未胡编）。**唯一暴露缺陷的题恰好是 Recall=0.667 的 CS-TN-003**：2023 表存在于稀疏索引（`chunk-3e7b9fcceb58079f032479c73fd63634`）且在候选池内，但融合后排在 13（reranker 对数字表失明，见 #9 探针），超出任何窗口而非召回缺口。结论：CP 0.4 级噪音块不干扰生成，Recall 0.917 是实际可用性的主要约束。报告见 `qa_v510_table_numeric.json`。
