## 0. 设计原则

### 0.1 三条铁律

1. **垂直域原则**：一个知识库 = 一个垂直业务域，不混合跨越大的领域。评测分数要能反映系统在该域真实使用时的表现。
2. **从问题反推文档**：先列真实用户会问的问题，再按问题组织文档内容。不要先随便写文档再从里面抠题。
3. **宁少勿滥**：5 篇高质量、有结构、有交叉的文档 > 20 篇东拼西凑的文档。测试集同理。

### 0.2 为什么是「客服中心」场景（方案 A）

- 现有 3 篇默认库文档（投诉 SOP / 智能客服 PRD / 销售业绩复盘）都能直接复用或轻度改造，改造成本最低。
- 客服是 RAG 最典型的落地场景之一，面试官熟悉、有共鸣。
- 天然包含：制度规范 / 产品文档 / 数据报表 / 话术 / 行业报告 等多种文档类型，评测覆盖面广。

### 2.3 内容设计要点（贴近真实业务）

#### 共享实体（图路价值的基础）

以下实体必须出现在至少 2 篇文档中，形成图谱中的连接边：

| 实体 | 出现文档 | 关系类型 |
|---|---|---|
| 三级投诉 / 一级投诉 / 二级投诉 | D1, D3, D4 | 分级标准 ↔ 实际数据 ↔ 话术应对 |
| 智能问答引擎 | D2, D3, D5 | 产品功能 ↔ 运营数据 ↔ 行业趋势 |
| 平均响应时长（ART） | D2, D3 | 产品指标 ↔ 实际运营数据 |
| 华东大区 / 华北大区 / 华南大区 | D3, D6 | 区域数据 ↔ 人员培训 |
| 工单系统 v3.0 | D2, D7 | 产品 ↔ 跨部门流程 |
| 王小燕（客服总监） | D1, D3, D6 | 责任人 ↔ 数据汇报 ↔ 培训组织 |

> 没有共享实体，图路的 1-hop 优势体现不出来，ablation 里「加图召回」那行分数不会动。

#### 刻意设计的易混淆点（检验检索质量）

| 混淆点 | 文档 A | 文档 B | 测试点 |
|---|---|---|---|
| 「响应时间」含义不同 | D1 投诉 SOP：客户投诉响应时限（24h/48h/5工作日） | D2 PRD：系统响应时间（< 2 秒） | 检索能否根据 query 语境区分 |
| 「升级流程」指向不同 | D1：投诉升级流程（一级→二级→三级） | D7：跨部门升级流程（客服→技术→产品） | 比较类问题的检索精度 |
| 「解决率」口径不同 | D2：产品目标解决率（≥ 85%） | D3：Q3 实际解决率（81.2%） | 数字类问题能否区分目标 vs 实际 |

#### 版本迭代痕迹（真实知识库的特征）

- D2 PRD 是 v2.1，文中提到「v1.0 版本已下线」「相比 v1.0 新增了 3 个功能」。
- D1 SOP 文末有「修订历史」表格，记录了 3 次版本变更。
- 作用：测试检索能否正确返回最新版本的信息，而不是过时的。

#### 跨文档引用

- D1 SOP 第 4.2 节：「话术规范详见《客服话术规范》第 3 章」→ D4 真的有第 3 章。
- D2 PRD 第 2.3 节：「运营指标定义参照《Q3 运营数据报表》附录 A」→ D3 真的有附录 A。
- 作用：测试系统是否顺着引用关系找到答案（图路的关系边能派上用场）。

## 4. 测试集设计（客服业务库最小集 35 题）

### 4.1 题型分布（35 题）

| 类别 | 数量 | 难度 | 设计说明 |
|---|---|---|---|
| **事实问答（单文档）** | 10 | ★☆☆ | 每篇文档至少 2 题，覆盖文档核心内容 |
| **事实问答（跨文档）** | 7 | ★★☆ | 必须综合 2+ 篇文档的信息才能完整回答 |
| **专名 / 术语查询** | 6 | ★★☆ | 中文专名、术语缩写、产品模块名 |
| **对比 / 差异问答** | 4 | ★★★ | 同级比较、易混淆概念区分 |
| **数字 / 表格问答** | 4 | ★★☆ | 来自 D3 报表的表格数据 |
| **综述 / 总结类** | 2 | ★★★ | 需要归纳多个段落/章节 |
| **无法回答（拒答）** | 2 | ★★☆ | 材料中没有答案，系统应拒答 |

**合计 35 题**。完整版补到 50 题时按同比例扩充。

### 4.2 题目来源（从真实问题反推）

出题顺序：

1. **先列 40-50 个真实用户问题**（模拟客服人员 / 运营人员 / 产品经理会问什么）。
2. 从中筛选 35 道「有明确答案、有区分度」的题。
3. 再回头补/改文档，确保每题都有可靠的 ground truth 来源。

**示例问题清单（草拟，正式测试集需按文档实际内容校对）**：

**fact_single（10 题）**：
- 客户投诉分为几级？各级响应时限是多少？（D1）
- 智能客服系统的核心业务目标有哪些？（D2）
- Q3 客服工单总量是多少？环比增长多少？（D3）
- 客服接起电话的第一句标准话术是什么？（D4）
- 2026 年客服智能化市场规模预计达到多少？（D5）
- 投诉升级到二级后，由谁负责跟进？（D1）
- 智能客服的多轮对话支持多少轮？（D2）
- Q3 哪个大区的工单解决率最高？（D3）
- 客服话术的三大禁忌是什么？（D4）
- 行业报告中提到的 Top3 竞品是哪三家？（D5）

**fact_cross_doc（7 题）**：
- 智能客服系统设定的解决率目标是多少？Q3 实际达到了多少？差距在哪？（D2 + D3）
- 一级投诉的响应时限要求是什么？Q3 一级投诉的实际平均响应时长是多少？（D1 + D3）
- 智能问答引擎在产品中的定位是什么？Q3 它承担了多少比例的工单？（D2 + D3）
- 投诉处理流程中，哪些环节需要用到工单系统？（D1 + D2）
- 客服话术规范中提到的「同理心表达」和 SOP 里的哪条原则对应？（D4 + D1）
- Q3 华东大区的人均工单数是多少？是否超过了行业报告中的健康阈值？（D3 + D5）
- 产品文档中的「知识库自学习」功能和行业报告里提到的哪个趋势对应？（D2 + D5）

**proper_noun（6 题）**：
- 什么是 ART？（D2/D3）
- 「智能问答引擎」和「工单系统 v3.0」分别是什么？（D2）
- 什么是三级投诉？（D1）
- FCR 是什么意思？Q3 的 FCR 是多少？（D3）
- 王小燕是谁？她在投诉处理中扮演什么角色？（D1/D3）
- 什么是「情绪识别模块」？它在哪个版本中加入的？（D2）

**comparison（4 题）**：
- 一级投诉和三级投诉有什么区别？（分级标准、响应时限、处理人）（D1）
- 「响应时间」在投诉 SOP 和产品需求文档中的含义有什么不同？（D1 vs D2）
- 华北大区和华东大区 Q3 的运营数据对比如何？（工单量、解决率、ART）（D3）
- 智能客服 v1.0 和 v2.1 的主要区别是什么？（D2）

**table_numeric（4 题）**：
- Q3 各渠道工单量分别是多少？占比最高的是哪个渠道？（D3 表 1）
- Q3 各月工单量趋势是怎样的？9 月比 7 月增长了多少？（D3 表 2）
- 各大区的客服人员数量和人均工单数分别是多少？（D3 表 3）
- Q3 的首问解决率（FCR）是多少？是否达到了目标？（D3 表 1 + D2 指标）

**summary（2 题）**：
- 请总结 Q3 客服运营的整体情况（成绩、问题、趋势）。（D3）
- 智能客服系统 v2.1 相比 v1.0 新增了哪些功能？这些功能分别解决了什么问题？（D2）

**unanswerable（2 题）**：
- 客服中心 2027 年的预算是多少？（材料中没有）
- 公司 CEO 叫什么名字？（材料中没有）

### 4.3 单条测试用例格式

与 [M9_evaluation.md §3.2](M9_evaluation.md#32-单条测试用例格式) 一致。补充两个字段：

```json
{
  "id": "cs_q001",
  "collection": "eval_cservice",
  "category": "fact_single",
  "question": "客户投诉分为几级？各级响应时限是多少？",
  "ground_truth": "投诉分为三级：一级（紧急，24小时内响应）、二级（重要，48小时内响应）、三级（一般，5个工作日内响应）。",
  "key_facts": [
    "投诉分为三级",
    "一级=紧急=24小时内响应",
    "二级=重要=48小时内响应",
    "三级=一般=5个工作日内响应"
  ],
  "must_have_docs": ["D1_客户服务投诉处理SOP.md"],
  "must_not_have_docs": ["D5_2026客服智能化行业趋势报告.pdf"],
  "difficulty": "easy",
  "source_docs": ["D1"],
  "tags": ["投诉分级", "响应时限"]
}
```

**新增字段说明**：
- `collection`：所属知识库，多库评测时用。
- `must_not_have_docs`：干扰文档列表——用于 precision 评测（这些文档出现在 top-k 就算 precision 扣分）。
- `source_docs`：题目来源文档编号，方便追溯。
- `tags`：题目标签，用于分类统计和细粒度分析。

## 5. 文档构造流程（最小集）

### 5.1 优先级与顺序

```
Step 1: D3 改造（销售复盘 → 客服运营报表）   ← 唯一需要大改的文档，先做
Step 2: D4 新增（客服话术规范+FAQ）           ← 纯文本，好写
Step 3: D5 新增（行业趋势报告）               ← 干扰项，不需要太精细
Step 4: 校对 D1/D2 现有文档，补共享实体        ← 确保跨文档连接
Step 5: 出 35 题 + ground truth + key_facts   ← 必须等文档定稿再出
```

### 5.2 D3 改造要点

把现有的「季度销售业绩复盘报告.pdf」改造为「2026 Q3 客服运营数据报表.pdf」：

- 保留：表格结构、排版风格、页数（约 6 页 3 张表）。
- 替换：所有销售相关指标 → 客服运营指标。
- 三张表：
  - 表 1：Q3 整体运营指标总览（工单总量 / 解决率 / FCR / ART / 满意度）
  - 表 2：分月工单量与趋势（7 月 / 8 月 / 9 月 + 环比）
  - 表 3：各大区运营数据对比（华东 / 华北 / 华南 / 西南：工单量 / 人员数 / 人均工单 / 解决率）
- 正文：约 1500 字的分析解读 + 存在问题 + 下季度计划。
- 格式：PDF，MinerU 解析。

### 5.3 D4 新增要点

客服话术规范与常见问题 FAQ：

- 结构：第 1 章 总则 → 第 2 章 基础话术规范（问候/道歉/转接/结束语） → 第 3 章 常见问题 FAQ（30+ 条，分 5 类） → 第 4 章 禁忌用语 → 第 5 章 语气与态度要求。
- FAQ 分类：账户类 / 订单类 / 投诉类 / 产品功能类 / 其他。
- 每条 FAQ 含「标准问法 + 标准回答 + 关联SOP章节」。
- 格式：MD，纯文本。

### 5.4 D5 新增要点

2026 客服智能化行业趋势报告：

- 结构：行业概览 → 市场规模 → 技术趋势 → 竞品分析 → 未来展望。
- 特点：信息密度低、概念性内容多、具体数据少。
- 作用：作为 precision 的干扰项——大部分具体问题的检索结果里不应出现这篇。
- 格式：PDF，约 10 页。

### 5.5 现有文档补充（D1 / D2）

在不改变原文主体结构的前提下，**补加共享实体和交叉引用**：

- D1（投诉 SOP）：加几处「相关话术参见《客服话术规范》」的引用；在责任人里加「王小燕（客服总监）」。
- D2（智能客服 PRD）：在指标部分加「目标 ART < 30 秒 / 目标解决率 ≥ 85%」；加「工单系统 v3.0」作为对接系统；加 v1.0 vs v2.1 对比表。

## 6. 质量检查清单

### 6.1 文档质检

- [ ] 每篇文档有清晰的多级标题（H1/H2/H3）
- [ ] 至少 6 个共享实体重现在 2+ 篇文档中
- [ ] 至少 3 处跨文档引用
- [ ] 至少 2 组易混淆概念（同词不同义 / 近义词不同文）
- [ ] 有版本迭代痕迹（修订历史、版本对比）
- [ ] 包含 1 篇弱相关干扰文档（precision 测试）
- [ ] 覆盖 PDF / DOCX / MD 三种格式
- [ ] 至少 1 份含表格的 PDF / DOCX

### 6.2 测试集质检

- [ ] 每题都有明确的 ground_truth（可在文档中定位到）
- [ ] 每题的 key_facts 是原子事实点（可独立判定正误）
- [ ] 7 类题型全部覆盖，比例与 §4.1 一致
- [ ] 跨文档题确实需要 2+ 篇文档才能完整回答
- [ ] 拒答题在所有文档中确实找不到答案
- [ ] 数字题的答案来自表格，不是正文里顺带提的
- [ ] 每题的 must_have_docs 正确（人类标注）
- [ ] 难度分布合理（易:中:难 ≈ 4:4:2）

### 6.3 评测前验证

- [ ] 人工跑 5 道题，确认系统能找到正确答案（不是全错）
- [ ] 人工跑 5 道题，确认 ground_truth 的措辞和系统答案的风格不会让裁判误判
- [ ] LLM 裁判 + 人工的一致性 ≥ 80%（10 题抽检）

## 7. 文件存放规范

```
backend/
├── inputs/
│   ├── raw/                      # 原始文档（已有，不动）
│   └── testset_corpus/           # 评测语料（新增，专用于评测）
│       ├── eval_cservice/        # 客服业务库
│       │   ├── D1_客户服务投诉处理SOP.md
│       │   ├── D2_智能客服系统产品需求文档.docx
│       │   ├── D3_2026Q3客服运营数据报表.pdf
│       │   ├── D4_客服话术规范与FAQ.md
│       │   └── D5_客服智能化行业趋势报告.pdf
│       └── eval_admin/           # 办公行政库
│           ├── A1_办公用品领用管理办法.pdf
│           ├── A2_员工差旅报销管理制度.docx
│           └── A3_IT设备管理与领用规范.md
│
└── tests/
    └── testsets/
        ├── testset_cservice_35.json    # 客服库 35 题（最小集）
        ├── testset_cservice_50.json    # 客服库 50 题（完整版）
        ├── testset_admin_15.json       # 行政库 15 题（最小集）
        ├── testset_admin_30.json       # 行政库 30 题（完整版）
        └── testset_smoke_10.json       # 冒烟集（跨库各 5 题，快速验证）
```

- 评测语料**不要和默认库混在一起**——默认库是演示用的，评测语料是受控资产。
- 测试集 JSON 入 git（= 代码资产）。
- 评测语料文件（PDF/DOCX/MD）也入 git（体积小、是评测的一部分）。
